# MediaSail 开发方法

用户于 2026-10-19 指定本项目后续开发使用 `mattpocock-skills`。插件提供的是设计、排错、测试和审查方法，现有 Electron、Python 和业务能力仍是软件实现。

## 按任务使用技能

使用当前安装的 `mattpocock-skills:` 插件技能，先阅读其 `SKILL.md`，再按实际需要读取引用资料。无需每个任务执行整套技能，也不把插件复制成另一份个人技能。

| 任务 | 技能 | 应产生的结果 |
| --- | --- | --- |
| 设计 Interface、重构模块 | `codebase-design` | 调用者、Interface、不变量、错误行为、依赖和 Seam 清楚；复杂性集中在有实际 Depth 的 Module 中 |
| 业务概念或关系存在歧义 | `domain-modeling` | 结合真实场景和代码澄清术语；确定的概念再写词汇表，重大取舍才写 ADR |
| 故障、错误或性能回退 | `diagnosing-bugs` | 先取得能捕捉原症状的反馈循环，再验证假设；修复后复查原场景并清理临时诊断 |
| 重要行为变更与回归保护 | `tdd` | 在事先约定的 Seam 上，每次一个行为、一个红绿循环；用结果而非内部实现作断言 |
| 审查一组改动 | `code-review` | 按技能取得用户提供的比较基线和需求来源，分别报告 Standards 与 Spec；两者不能互相替代 |
| 编写 Skill、AGENTS 或 Agent 参考资料 | `writing-for-agents` | 简短入口、明确查阅条件、按需展开；同一事实有清楚的权威来源 |
| 调研、验证设计假设、编写 PR | `research`、`prototype`、`pr` | 按对应技能收集证据、回答设计问题或交付可审查的说明 |

任务已有确认方案时，复用其中的基线、范围和验收约定。TDD 要求的测试 Interface 与 Seam 在写测试前与用户确认；已有确认覆盖当前行为时沿用，不对每个测试重复询问。纯文案、图标和低影响排版按实际影响选择检查。

## 开发与验证

1. 明确一个具体行为及其完成标准，区分已复现问题、静态风险和设计建议。
2. 找到调用者实际使用的 Interface。保留已有有效实现，只在真实变化或测试需要处设置 Seam。
3. 按所用技能完成该切片。格式整理与行为变化分开，避免用大范围机械改写掩盖差异。
4. 执行与改动相关的检查，并检查它覆盖了什么、没有覆盖什么。真实平台与真实安装行为需要相应环境证据。
5. 使用约定基线审查需求与规范。新增行为、兼容变化和未验证项在交付中说明。

现有运行命令、锁定版本和构建配置以仓库配置及脚本为准，本文件不另存一套副本。首次梳理发现本地构建、源码 CI 与发布验证入口尚不统一；整理前应核对各自实际执行内容，不能把其中一个通过等同于全部通过。

## 兼容约定

- 继续沿用已发布安装的身份、位置选择、更新频道和资料发现方式。安装相关修改使用隔离环境核对旧版升级、登记、快捷方式、旧程序清理和重新启动。
- 资料库由用户选择，之后更新沿用选择；切换只改变位置，旧资料留在原位。现行选库行为不依赖旧版失败迁移任务。
- 保留现有画像、项目及业务记录格式。技术标识和兼容别名按契约处理；显示名称规范化与存储格式变更分别评估。
- 用户修改的画像、方法、工具、Skill 和项目内容继续保留。文件冲突、写入失败或结果未知时保留可恢复信息，不把空值或不确定结果当成已成功保存。
- 项目阶段是人工登记；平台发布结果与本地发布记录是不同事实。分析历史比较需要明确账号、平台、来源和口径。
- MediaSail 提供画像、业务工具、分析资料和成果管理，外部 Agent 承担智能工作。产品 Skill 保持开放指导，不因开发规范增加用户 Agent 的固定执行链。

上述内容是现有兼容目标，不代表每项能力已经覆盖所有场景。具体缺口及建议见 [2026-10-19 工程讨论](ENGINEERING-REVIEW-2026-10-19.md)。

## 文档与发行原件

业务事实优先核对实现、生成的接口结构和可执行示例。接口解释、前端调用及 Skill 的修改随对应行为一起验证。用户可写的资料库副本继续使用已有冲突保留机制。

固定上游和补丁复现暂时保留；上游变更从原件修改并导出，不能仅修改一次性的打包产物。后续整理源码包时需把根目录开发指引与相应参考文档一起包含。

架构讨论只产生建议，不自动触发大规模改写或版本发布。正式发行沿用已经确认的候选安装、资产核验与 GitHub 发布流程。
