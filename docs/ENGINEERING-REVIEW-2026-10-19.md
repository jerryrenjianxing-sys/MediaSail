# MediaSail 工程讨论：2026-10-19

## 范围和结论

针对用户提出的“使用 mattpocock-skills 重新开发或重新规范设计”，三位子智能体分别阅读架构、验证发布流程、业务数据与 Agent 接入，主智能体交叉核对。基线为已发布 0.5.5 后的提交 `8d40a92`。

建议先规范，再按业务切片重构。目前没有足够证据支持整体重写。现有画像、分析公式、内容库、登录发布、资料库保护与真实升级验证应继续使用。本轮只补开发指引，未运行新的业务或安装验收；以下静态风险不能当成已经复现的用户故障。

## 值得保留的实现

- [资料库选择](../desktop/library.cjs) 把路径检查、库身份、初始化、串行选择与位置提交放在小 Interface 后。
- [发行文件同步](../desktop/workspace.cjs) 的 `syncManaged` 统一处理发行基线、用户修改、冲突和备份。
- 固定上游的 `skills/shared/scripts/manifest.py` 提供项目登记读写，供 HTTP 和 CLI 复用；已有 revision、增量字段更新及原子替换。相关行为检查见 [test_output_metadata.py](../tests/test_output_metadata.py)。
- 上游版本、依赖及暂存文件有锁定与哈希核对；隔离 Windows 的真实安装验收检查路径、登记、数据和连续重启。这些证据应继续发挥作用。

## 优先风险与改进理由

| 发现 | 代码依据 | 建议 |
| --- | --- | --- |
| 离开编辑页面的保护来源不一致 | 前端 `App.tsx` 切页及 `lib/appStorage.ts` 退出主要读取项目归档状态；`lib/unsaved.ts` 已登记多个页面，桌面切库读取该通用状态 | 先复现具体场景，再让切页、切换画像、退出、安装更新和切库使用一致的编辑状态判断 |
| 画像保存缺少服务端版本冲突核对 | 后端 `web/app.py` 的画像 PUT 使用固定 `.md.tmp`，整文件替换且无 revision；前端读取后再保存仍有竞争窗口 | 增加兼容的冲突保护与独立临时文件；保留六维文件及用户自定义文件，说明直接文件操作能保证与不能保证的行为 |
| 平台结果与记录结果未充分分开 | 原生发布执行主要按进程退出码判断，日志和排期写入异常被忽略 | 分清平台已确认、失败、未知，以及本地记录状态；记录失败只补记录，不据此重新发布 |
| 三套分析历史归属口径不同 | 账号观测按平台、稳定账号和来源比较；手工 tracker 按画像、平台、日期记录；发布日志缺少部分稳定归属信息 | 先统一解释与契约，保留历史及公式；后续兼容添加必要归属字段，避免强行合并数据 |
| 源码 CI、本地构建、发行验收覆盖内容不同 | [check.yml](../.github/workflows/check.yml) 未构建前端；[build.ps1](../scripts/build.ps1) 未统一执行 Python suite；源码包和发行校验另行运行 | 建立共同检查入口；候选发行另执行真实安装场景，证据关联同一提交及安装包哈希 |
| 升级验收容易逐版复制 | [verify-content-upgrade-ci.cjs](../scripts/verify-content-upgrade-ci.cjs) 固定 0.5.4 → 0.5.5 等场景 | 保留历史证据，把当前 runner 与场景输入分开，下一版复用 |

当前上游补丁涉及约 4.1 万行、94 个文件差异段。这说明修改归属和定位成本较高，不能单凭大小推断实现质量。方法文本也在 [curate-knowledge.cjs](../scripts/curate-knowledge.cjs) 中被加工；后续要检查最终发行内容，逐步减少依赖正文措辞的隐式替换。

## 建议推进顺序

### 第一阶段：工程基线

梳理已经采用的业务词汇和关键兼容契约，统一源码检查入口，明确前端、Python、桌面、补丁复现和候选安装分别证明什么。重大取舍才写 ADR；不为了文档数量拆出大量空文件。

完成标准：同一提交在开发机与 CI 使用一致的源码检查，生成资料与补丁可核对；下一轮测试位置和验收范围清楚。

### 第二阶段：可靠编辑

先完成“编辑后能否安全离开”的单个切片，再完成画像的可靠保存。每个切片先约定 Interface 与测试 Seam，分别验收后再继续，不一次改掉整个数据层。

重点观察：取消切页或退出后草稿仍在；保存中不会被静默打断；外部修改能明确提示；写入失败不破坏旧文件。API 写入之间的冲突保护与任意外部文件编辑不是同一种保证，设计时需分别说明。

### 第三阶段：运行与业务结果

将桌面启动、退出、更新、切库的协调集中到明确的生命周期 Module；随后整理账号校验、业务任务活动状态、发布结果与记录结果。保留现有 HTTP、脚本与文件调用方式，不扩成通用任务调度。

### 第四阶段：源码归属与发行维护

在前两轮切片取得真实收益后，再比较正式维护 fork、收窄补丁或逐步自有化特定 Module。每种方案核对可读性、修改集中程度、上游追踪、许可和可复现构建成本；不同时更换源码组织、数据格式及安装机制。

## 下一轮建议的验收位置

这些是待随实施方案确认的 Seam，本轮未新增测试：

- 可见界面操作：捕捉草稿、保存中及用户取消离开；不能证明磁盘持久化和真实平台结果。
- 画像读写 Interface：捕捉服务端冲突、写入失败和文件保留；另评估 Agent 直接文件编辑的竞争场景。
- 资料库选择与进程重开：捕捉位置、身份和连续启动；不替代浏览器登录验收。
- 业务脚本公开调用：固定样本与独立算例核对原计算口径。
- 真实安装器入口：核对登记、目录、资料及重启；下载测速与安装验收分别记录。

产品随附 Skill 的现有开放结构、实时路径发现和实例核对继续保留。开发方法的采用不增加外部 Agent 的每轮仪式，个人安装元数据继续保留 `allow_implicit_invocation: false`。
