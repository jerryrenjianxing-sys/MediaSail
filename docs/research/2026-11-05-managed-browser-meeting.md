# MediaSail 专用浏览器方案：三方审查汇总

日期：2026-11-05。用户要求先开会审查可行性。本轮进行了三项独立只读审查，并核对官方资料及现有实现；没有安装/启动候选、操作网站或账号，也没有构建或发布版本。这是方案讨论记录，不是实施通过声明。

## 会议结论

**有条件支持“软件自带可见专用 Chromium + BrowserSkill + 原有观测回存”的方向，先验证最小闭环，暂不批准正式内置与发行。** 原有 Edge/Chrome 商店安装和调试开关不再作为默认接入路径；用户在专用浏览器中完成首次网站登录及平台必要验证。外部 Agent 已有能力时直接复用。

“技术上可以内置”指扩展预载、本地连接和独立浏览器资料有源码/机制依据，不等于已有确切可发行构建，也不等于首次体验、平台兼容或生命周期已通过实测。现行 `SPEC-0.5.12.md` 仍记录上一轮 agent-browser 双浏览器方案；开始下一轮实现前，应以用户最终确认的新方案替换当前需求和验收表，保留历史研究。

三份独立意见：

- [技术可行性](2026-11-05-managed-browser-feasibility-review.md)：支持机制验证，浏览器具体产物、媒体能力和发行依据尚未确定。
- [产品与数据闭环](2026-11-05-managed-browser-product-review.md)：支持最小接入层，复用已实现的观测、画像和成果管理，避免另建调度与档案系统。
- [生命周期与维护](2026-11-05-managed-browser-lifecycle-review.md)：必须处理自动 Skill 同步、端口/身份、扩展状态和组件升级；不能直接复制原版程序便宣称隔离可靠。

## 必须纳入方案的修正

| 审查发现 | 事实边界 | 建议处理 |
| --- | --- | --- |
| 尚未确定浏览器发行包 | Chromium snapshot 不是受支持 stable 产品承诺；CfT 仓库 Apache 标签不覆盖其浏览器二进制。默认 Chromium 的 H.264/AAC 能力与品牌浏览器不同。 | 固定一个完整 Win64 构建，核对来源、哈希、对应许可及更新维护路径；在目标后台测登录、数据与常用视频样本，不能只测 `canPlayType` 或空白页。未测能力不随 BrowserSkill 支持范围自动获批。 |
| Electron 不能直接当作完整 Chrome 扩展宿主 | Electron 官方只支持部分扩展 API；BrowserSkill 依赖 debugger、offscreen、windows 等能力。 | 采用独立完整浏览器窗口；不把“Electron 已有 Chromium”视为无成本复用整个扩展的依据。 |
| 原版 daemon 会尝试同步外部 Agent 的已有托管 Skill | 启动代码异步调用 `sync_installed_skills`；`BSK_AUTO_UPDATE=off` 不关闭该行为。Windows Known Folder 也不能靠修改 HOME 可靠隔离。并非会无条件新装所有 Skill，但可能更新/恢复/收编已有安装。 | 在产品适配构建中明确关闭启动自动同步；保留用户主动安装的选择。不能在正式或本机验证中默认改动其他 Agent 配置，也不能仅设置 `BSK_HOME` 就宣称已隔离。 |
| 状态隔离不等于端口隔离 | 原版默认端口 52800；业务命令默认自启会采用默认参数。其他用户工具或另一资料库可能已有 daemon。 | 启动层明确准备并记录产品端口，CLI/扩展/daemon 保持一致；禁用回落到默认自启，核对协议及正确实例，目标离线不去掉选择器重试。 |
| 扩展 ID 不必固定才能握手，但升级状态需要稳定 | 无 manifest key 时 ID 可能随加载路径变化；Origin 接受规范 ID 不代表存储会自动跨 ID 延续。网站 cookies 与扩展存储是不同资料。 | 设计稳定扩展身份并验证跨版本路径变化；不可变版本缓存与扩展身份一并设计，不能升级后把新 instance 当作正常延续。 |
| daemon/扩展连接丢失会清理 session | 上游会在 transport loss 后停止本地 session、归还借用页、关闭 Agent Window；它不保证 daemon 重启对任务无感。 | 正常软件退出/切库/安装不重启独立工具组。在用时继续原组，关闭专用浏览器后再启用新版整组；故障后重新观察，不重放结果不明的写操作。 |
| 新专用浏览器与旧工具不是同一份登录 | 旧采集器/发布器仍通过自己的 `launch_persistent_context` 和平台资料目录启动。 | 本切片保留旧有效资料和折叠入口，说明独立登录；Agent 路径不要求旧工具先登录。以后如需统一旧工具，单独适配，不复制 Cookie 或并发启动同一 profile。 |
| 提取结果不等于完整账号历史 | BrowserSkill 提取的是已加载 DOM，不自动翻页；连接、网页登录、数据覆盖和落盘成功各有不同依据。 | 保存实际时间、账号依据、指标口径、范围、缺项和证据；观测/证据/报告分别读回。用户任务决定是否继续补取，Skill 不变成固定全量流程。 |

这些是已证实的上游行为或静态设计风险；尚不存在受管浏览器实现，不能把所有风险称作已复现的产品 bug。

## 建议的最小产品形态

- 一期只管理一套固定浏览器、CLI 与扩展，不因为曾比较 agent-browser 就默认把两套执行工具都打包。
- 每份资料库使用独立持久浏览器资料；平台账号从实际网页确认，不与运营画像、浏览器配置名称混为一谈。多 Agent 使用任务自己的 session，输出仍归原资料库。
- 浏览器由用户主动打开或 Agent 确需时启动；首页、查看历史、刷新和轻量 check/status 不启动浏览器或旧采集器。不强迫已有浏览器工具的 Agent 改用它。
- MediaSail、独立浏览器工具组和外部 Agent 会话分别管理生命周期。连接回执固定资料库和工具组，软件关闭后的 HTTP 下线不表示浏览器已经关闭；切库不接管旧会话。
- 缓存程序与持久登录分开；在用版本不原地替换，不自动清理在用缓存，不直接用旧浏览器降级打开已升级 profile。浏览器安全更新需要明确维护，不能永久冻结旧构建。
- 继续用既有账号观测 CLI/HTTP、项目与画像接口，不新建 MCP、远程命令服务、发布队列或 Agent 全局配置。AI 发布仍走现有默认浏览器官网入口。
- 本轮实测不公开发布内容；以后发布按用户具体任务授权，不新增必须手工点击最终发布的全局执行链。

## 下一步最小验证闭环

1. **固定试验材料。** 确定具体浏览器构建与所需能力，准备匹配 BrowserSkill；先处理自动 Skill 同步，完整记录来源及适配，不改日常安装或资料库。
2. **验证开箱接入。** 干净 Windows / 无全局 Node、Python / 中文空格路径中，一次入口打开可见浏览器、预载扩展并连接正确实例。记录用户实际需要的操作；进程启动或图标出现不算成功。
3. **验证抖音只读业务。** 用户在原生平台页面登录，重开复用；Agent 从创作者后台取一个明确范围样本，保存证据、登记观测、生成项目报告并在原页面读回。缺项和零分开，不把已加载列表当全量。
4. **验证持久化与故障。** 端口占用、另一套 BrowserSkill、重复连接、扩展/daemon 中断、用户关闭、软件退出/切库均不串库、不误连、不清登录、不盲目重放；验证外部 Agent 配置未被更改。
5. **验证升级后再发行。** 确定同组切换时机、扩展身份、登录保持和 profile 兼容，再完成隔离安装升级及同版覆盖。记录安装包、首次展开、运行缓存、用户资料的实际占用；通过后才走源码审查、草稿核验和正式发布。

本记录不把一次连接演示提升为所有平台/上传/发布支持认证，也不要求为了第一切片重验所有外部 Agent 自带工具。后续具体实现仍应采用已确认测试 Interface 做红绿验证，正式候选再执行 Standards/Spec 两轴代码审查。
